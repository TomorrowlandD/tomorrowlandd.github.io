## 一、先从一个常见的问题说起

假设你正在使用 Claude Code 开发项目。

你让 AI 修改一段代码，它很快完成了任务，但你发现：**它忘记运行 Prettier 格式化工具了。**

于是，你提醒它：“以后每次修改代码，都记得格式化。”

结果，下次修改时，它又忘了。

你可能会想：能不能在 `CLAUDE.md` 中写一条规则，让 AI 每次都遵守？

当然可以，但这里有一个问题：**大模型是概率性的，而不是严格按照程序逻辑执行的。**

即使明确告诉它“每次修改代码都要格式化”，它也可能因为任务复杂、上下文变化等原因遗漏这条指令。

对于代码风格这样的普通要求，偶尔遗漏可能还可以接受。

但对于某些操作，例如：

+ 禁止向主分支执行危险的 Git 操作
+ 修改代码后自动执行格式化
+ 完成任务前检查代码质量
+ 执行关键操作时记录日志

我们希望它们成为自动执行的规则，而不是依赖 AI 自己记住。

**这就是 Agent Hooks 要解决的问题。**

## 二、什么是 Agent Hooks？

Hooks，中文通常称为**钩子机制**。

简单来说，Hooks 允许开发者在 Agent 运行过程中的特定时刻，自动触发预先设置好的操作。

我们可以把 Agent 的执行过程理解成一条流水线：

**接收用户指令 → 思考任务 → 调用工具 → 获取结果 → 回复用户**

而 Hooks 就像安装在流水线不同位置的自动装置。

例如，我们可以规定：

+ Agent 准备执行命令时，先检查命令是否危险。
+ Agent 修改文件后，自动执行格式化工具。
+ Agent 准备结束任务时，自动检查测试是否通过。

这些操作不需要 Agent 主动想起来，而是由运行框架根据事件自动触发。

因此，理解 Hooks 只需要记住一句话：

**Hooks = 在 Agent 生命周期的特定事件上，自动执行预先配置的逻辑。**

这里有一个关键区别：

普通 Prompt 是告诉 AI“你应该做什么”。

Hooks 则是在运行框架中配置“某个事件发生时，执行什么操作”。

## 三、Hooks 是如何工作的？

一个 Hook 的执行过程可以拆成三个部分：

**Event（事件）→ Matcher（匹配器）→ Handler（处理器）**

### 1. Event：什么时候触发？

Event 就是 Agent 生命周期中的某个关键节点。

以 Claude Code 为例，常见事件如下：

| 生命周期事件   | 触发时机             | 典型用途               |
| -------------- | -------------------- | ---------------------- |
| `PreToolUse`   | 工具调用前           | 检查、拦截危险操作     |
| `PostToolUse`  | 工具调用成功后       | 自动格式化、检查代码   |
| `Stop`         | Agent 准备结束回复时 | 质量检查、要求继续修复 |
| `Notification` | 系统产生通知时       | 桌面提醒、消息推送     |
| `SessionStart` | 会话启动或恢复时     | 环境初始化、加载上下文 |

除此之外，还有 `SubagentStart`、`SubagentStop`、`PreCompact`、`WorktreeCreate` 等事件。

不需要记住所有事件，只需要理解：**Agent 在执行过程中会经过不同的节点，而 Hooks 可以在这些节点上自动执行操作。**

### 2. Matcher：哪些操作需要触发？

假设我们配置了一个 `PostToolUse` Hook。

难道 Agent 每次调用工具，都需要运行格式化程序吗？

显然没必要。

读取文件不需要格式化，搜索代码也不需要。只有修改文件时，才需要执行格式化操作。

这时候就需要 Matcher。

Matcher 相当于一个**过滤器**，用于决定哪些事件需要触发对应的 Hook。

例如：

| Matcher      | 含义                     |
| ------------ | ------------------------ |
| `Bash`       | 匹配 Bash 工具           |
| `Edit|Write` | 匹配编辑或写入文件的工具 |
| `*`          | 匹配当前事件下的所有目标 |

因此，我们可以配置：

**Event = PostToolUse，Matcher = Edit|Write**

意思就是：当 Agent 使用 Edit 或 Write 工具成功修改文件后，执行指定操作。

### 3. Handler：触发后具体做什么？

Handler 就是真正执行任务的部分。

例如，修改代码之后需要自动运行 Prettier，那么 Handler 就可以执行对应的 Shell 命令。

Claude Code 支持多种处理器：

| 类型     | 作用                      |
| -------- | ------------------------- |
| Command  | 执行 Shell 命令或脚本     |
| HTTP     | 向外部服务发送 HTTP 请求  |
| MCP Tool | 调用已配置的 MCP 工具     |
| Prompt   | 调用大模型进行判断        |
| Agent    | 启动子 Agent 进行复杂检查 |

对于大多数简单自动化任务，**Command 类型通常就足够了**。

例如使用 Python 脚本检查文件路径，或者调用 Prettier 格式化代码。

Prompt 和 Agent 类型适合需要语义理解或复杂推理的情况，但它们也会引入额外的模型开销和不确定性。

## 四、Hooks 能够实现哪些功能？

理解前面的机制后，我们来看几个实际例子。

### 场景一：自动格式化代码

**需求：** 每次修改代码后，自动运行 Prettier。

配置思路：

+ Event：`PostToolUse`
+ Matcher：`Edit|Write`
+ Handler：获取修改的文件路径，执行 Prettier

这样一来，只要 Agent 通过匹配的工具成功修改文件，就会自动触发格式化流程。

### 场景二：阻止危险操作

**需求：** 禁止 Agent 向 main 分支执行 `git push --force`。

配置思路：

+ Event：`PreToolUse`
+ Matcher：`Bash`
+ Handler：检查即将执行的命令，发现危险操作则拒绝

这个 Hook 会在命令执行前运行。

如果发现不符合规则，就可以阻止当前工具调用，并将拒绝原因反馈给 Agent。

注意：只匹配 Bash 并不能覆盖其他可能执行 Git 操作的工具，因此安全规则需要考虑完整的操作路径。

### 场景三：任务完成前自动检查

**需求：** Agent 完成代码开发后，自动执行测试。

配置思路：

+ Event：`Stop`
+ Handler：执行测试并检查结果

如果测试失败，Hook 可以阻止 Agent 结束当前回复，将错误信息反馈给它，让它继续尝试修复。

但这不意味着测试必然通过。Agent 仍可能无法修复问题，因此还需要合理的重试和终止策略。

### 场景四：自动发送通知

**需求：** Agent 需要人工批准某个操作时，自动发送桌面通知。

配置思路：

+ Event：`Notification`
+ Handler：调用系统通知命令

这样就不必一直盯着终端，可以在需要处理时再切换回来。

## 五、Hooks 应该如何配置？

在 Claude Code 中，Hooks 主要通过 `settings.json` 配置。

常见的三个位置：

| 配置文件                      | 作用范围                             |
| ----------------------------- | ------------------------------------ |
| `~/.claude/settings.json`     | 当前用户的所有项目                   |
| `.claude/settings.json`       | 当前项目，可以提交到 Git             |
| `.claude/settings.local.json` | 当前项目的本地配置，通常不提交到 Git |

例如，某个项目要求使用 Prettier 格式化，就可以将对应 Hook 写入项目级配置。

一个典型的 Hook 配置包含三部分：

**事件名称 + Matcher 匹配规则 + Handler 执行逻辑。**

Claude Code 也提供了 `/hooks` 命令，可以查看和管理当前配置。

## 六、Hooks 和 Prompt、权限系统有什么区别？

这是一个容易混淆的问题。

假设我们希望 Agent 不要修改 `.env` 文件。

可以使用三种方式：

| 机制               | 工作方式                                   |
| ------------------ | ------------------------------------------ |
| Prompt / CLAUDE.md | 告诉 AI 不要修改                           |
| Permission System  | 通过权限规则允许或拒绝操作                 |
| Hooks              | 在指定事件上执行自定义检查，必要时阻止操作 |

它们并不是互相替代的关系。

**Prompt 负责指导行为，权限系统负责访问控制，Hooks 负责事件驱动的自动化和自定义约束。**

Hooks 的优势在于灵活：除了拒绝操作，还可以记录日志、调用外部服务、执行格式化，以及向 Agent 反馈信息。

但要注意，Hooks 并不是绝对的安全保证。

例如，只拦截 `Write` 和 `Edit` 工具，并不能阻止 Agent 通过 Bash 修改文件。另外，Hook 自身也可能执行失败或超时。

因此，重要的安全约束通常需要结合权限系统、沙箱和 Hooks 共同实现。

## 七、Hooks 是 Agent 的必需组件吗？

看到这里，你可能会有一个疑问：Hooks 看起来很有用，但为什么日常使用 Claude Code、Codex 时，似乎很少接触到它？

其实，这是正常的。

Hooks 并不是 Agent 的必需组件，而是一种按需使用的增强机制。

对于大多数个人 Agent 项目，Agent Loop、Tool Calling、Context Engineering 等核心机制，通常已经足够支撑日常任务。

而且，很多需求本身就有成熟的解决方案。例如，代码格式化可以交给 IDE，自动测试可以交给 CI，危险操作也可以通过权限系统限制，不一定非要使用 Hooks。

那么，什么时候才需要 Hooks？

通常是当 Agent 系统逐渐复杂，需要更严格的行为约束和更灵活的功能扩展时。

例如：

+ 个人简单项目： 通常不需要 Hooks，核心功能能够正常运行即可。
+ 复杂 Agent 项目： 可以通过 Hooks 自动记录日志、检查工具执行结果、触发质量评测。
+ 企业级 Agent 系统： 可以通过 Hooks 接入安全审计、监控告警、权限检查等机制，提高系统的可控性和可扩展性。

所以，Hooks 的价值主要体现在两个方面：

第一，提高系统的可靠性下限。 将部分依赖 AI 主动判断的操作，变成运行框架自动触发的规则，减少遗漏。

第二，提高系统的扩展上限。 在不频繁修改 Agent 核心逻辑的情况下，增加新的自动化能力。

当然，Hooks 不是实现这些功能的唯一方案，中间件、事件机制等也能承担类似职责。

因此，对于初学者而言，理解 Hooks 的设计思想，比急着掌握复杂的 Hook 配置更重要。

## 八、使用 Hooks 的几个建议

**第一，优先处理真正需要自动化的事情。**

例如自动格式化、危险命令检查、任务完成提醒。没有必要为每个细节都创建一个 Hook。

**第二，尽量使用简单、确定性的规则。**

能通过路径匹配、条件判断解决的问题，就不必调用大模型。这样不仅执行更快，而且结果更容易预测。

**第三，注意执行性能与失败处理。**

Hook 需要消耗执行时间。如果在每次工具调用前运行一个耗时脚本，就可能明显拖慢 Agent。

对于安全关键的 Hook，还应设置合适的失败处理策略，避免检查程序报错后操作被意外放行。

## 九、总结

Hooks 的核心价值，是让 Agent 的某些行为不再依赖模型的主动判断，而是由运行框架自动触发。

它的工作机制并不复杂：

**Event 决定什么时候触发，Matcher 决定匹配哪些目标，Handler 决定具体执行什么操作。**

联系前面介绍过的 Agent 机制：

SubAgent 主要解决上下文隔离问题，Agent Teams 解决多 Agent 协作问题，Worktree 帮助隔离文件工作空间。

而 Hooks 关注的是另一个维度：

**如何为 Agent 增加可重复执行的自动化规则和行为约束？**

随着 Agent 能够自主执行越来越复杂的任务，我们不仅需要让 AI 知道应该做什么，还需要通过工程机制，确保关键流程受到可靠的控制。

这也是 Agent Hooks 的意义所在。
